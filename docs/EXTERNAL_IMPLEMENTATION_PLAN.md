# External handoff execution — 2026-10-12

The owner selected **UnifiedPush, a user-held recovery secret, and signed device addition/revocation** on 2026-10-12. This approves the product direction below, not an independent security review. None of these new protocols is shipped by this document. Existing clients still have no account recovery or real push integration. No physical device, operator pin set, signing key, distributor endpoint or independent reviewer was supplied. The build host's `adb devices -l` returned an empty device list.

## Push and metadata (ST-017, ST-009, ST-042)

Use opt-in UnifiedPush with no embedded FCM fallback, analytics or contact-derived collapse identifiers. Keep push disabled by default in the privacy profile. Users choose a distributor and explicitly accept the disclosure of wake times and installation linkage. Changing distributor unregisters the old endpoint; disabling push deletes relay registration and cancels unsent wakes.

The **decrypted application payload** is always the exact bytes `{"v":1}`. Wire payloads need not be constant: the current [UnifiedPush Android specification](https://unifiedpush.org/developers/spec/android/) requires RFC 8291 encryption. Implement that through a maintained, reviewed Web Push library, with independently generated per-registration keys outside the message vault. These keys permit content-free wake handling while locked, never message decryption. Keep endpoint credentials and push keys out of logs, backups and the FFI's ordinary return values. A locked wake displays only a generic notification after permission checks; it must not unlock the vault or fetch using unavailable vault-held credentials.

Register through the existing signed relay channel with a fresh nonce, endpoint, push public key, auth secret and monotonic registration generation. The HTTP notifier needs bounded timeouts, bounded responses, no redirects, public-address checks **on every resolution and connection**, a restricted operator allowlist and separate egress policy. Reject loopback, link-local, private, multicast and other non-global destinations; an allowlisted hostname alone is insufficient against DNS rebinding. Operator overrides for a private self-hosted distributor must be explicit and isolated from relay/database administration networks. This follows the [UnifiedPush application-server SSRF guidance](https://unifiedpush.org/developers/intro/).

The spec also recommends endpoint possession confirmation. A random registration challenge would violate the current constant-wake interface. Before integration, review one explicit exception: an encrypted, single-use **registration-only** challenge containing no account, sender or conversation identifiers, accepted only during an authenticated registration handshake. Message wakes remain constant. Do not silently reuse `WakeHandler` for this challenge or enable an unconfirmed endpoint. The existing `PushNotifier::wake(token)` abstraction must become a typed registration plus notifier boundary; it currently cannot carry Web Push encryption parameters safely.

Queue wakes separately from request handling. Coalesce by device, with no message counts; permit at most one wake per 30 seconds, a short queue TTL, bounded retries and jitter. Do not claim that batching defeats timing correlation. Invalid/expired endpoints are removed only for the registration generation that failed, so a late response cannot delete a newer registration. No endpoint URL or token may enter metrics labels. Suppress wakes for revoked devices.

**First metadata step:** reuse the already implemented recipient-issued delivery capabilities; do not invent an additional sender certificate or stable sender token. Define a versioned application-delivery envelope containing only an opaque capability, padded ciphertext and random idempotency identifier. Move application group ID, epoch, content type and device identifiers into the authenticated E2EE frame. The relay enforces per-capability quotas without a sender account identifier. Commit ordering, initial introductions and group administration retain their existing authenticated lanes and their documented leakage. Recipients verify the E2EE sender and epoch; malformed, wrong-group and replayed frames are rejected before history persistence. Review capability revocation races, cross-relay attachment authorisation and deduplication-linkability before changing wire types. The relay still knows recipient/capability mapping, size classes and timing; UnifiedPush still adds endpoint and wake timing linkage. This is a reduction in application-envelope fields, not anonymity.

Required integration tests: exact decrypted wake bytes, registration challenge isolation, SSRF/rebinding/redirect rejection, malformed and forged broadcasts, endpoint rotation racing with a delayed provider failure, duplicate wakes, revoked-device suppression, opt-out deletion, notification permission denial, locked-vault handling, Doze and OEM battery restrictions. No real distributor or physical-device delivery evidence exists yet.

## Account authentication, recovery and revocation (ST-010, ST-020, ST-033)

Prefer **account control recovery without past-message recovery**. Generate a separate high-entropy recovery signing seed on-device using the OS CSPRNG; encode it with a version and checksum for an offline recovery card. Never use a user password as this seed, upload it, escrow it, or derive MLS/history keys from it. The owner keeps it offline; losing every device and this card loses account control. A stolen card grants account control and is an explicitly disclosed risk. The normal vault stays hardware-bound and excluded from backup.

Create a versioned account authority record: random account ID, account-authority public key, recovery public key, generation, active device records and revocation tombstones. The recovery seed authorises **authority replacement**, not daily device requests. Existing devices use a distinct account-authority signing key stored in their vaults; each device keeps its own MLS identity and transport key. A new record includes the previous record hash, operation ID, new generation, authority/recovery keys, target device identities and signatures over a canonical, domain-separated encoding. Keep account/device/audience/version binding from current signed requests. Do not treat the shared invitation token as account authentication.

Normal device linking: display a QR with an ephemeral encrypted pairing channel, fresh nonce and new-device public keys; the existing device verifies a short code with the new device, then signs the exact device binding and authority generation. The new device demonstrates key possession. Initial enrollment must pin the authority/recovery keys at contacts; subsequent directory changes cannot be trusted merely because the relay returned them. Recovery records form a signed successor chain; reject gaps, equivocation and rollback below the highest locally pinned generation. A hostile relay can withhold this chain. Gossip/key transparency is still absent; do not claim a first-time or long-offline client detects every split view.

Lost-all-devices recovery: the user explicitly imports the offline card on the new phone, verifies the intended account, signs a new generation with a new authority and new device keys, and marks all prior devices revoked. Rotate the recovery seed after this ceremony and export the replacement card before discarding the old one. Relay updates must be atomic compare-and-swap on the expected generation; retries return the same result for the same signed operation, conflicting content fails. No endpoint can reset recovery keys using email, SMS, invitation token or relay administrator authority. The imported recovery secret crosses the UI boundary only in this explicit ceremony; it requires a dedicated zeroisation and screen/clipboard review (ST-027 remains relevant).

Revocation has two distinct effects. The honest relay rejects the revoked device's authenticated requests and removes its push registration, unclaimed KeyPackages and capabilities. Contacts independently reject the revoked device and rotate their delivery permissions when they receive the valid account record. Group owners issue MLS Remove commits for **each device leaf** and remaining clients process them; only then are new epoch secrets inaccessible to the revoked member. [RFC 9420 §§12.1.3 and 16.6](https://www.rfc-editor.org/rfc/rfc9420.html) define the relevant Remove/epoch security. A malicious relay or group member can delay this transition. Show pending per-group revocation and require a new group if the home log is blocked; do not display "revoked everywhere" on relay acknowledgement alone. Old plaintext/copies remain unrecoverable from hostile endpoints, and no remote wipe is promised.

This requires wire-v2 records, directory validation, engine persistence, MLS credentials, contact cards, UI, migrations and two-device end-to-end tests. Existing random account IDs and pinned **device** identity keys do not automatically pin the proposed authority root. Migration must be endorsed by the already trusted device, retain the old verification anchor until explicit confirmation, and display a security event. Existing accounts cannot be "recovered" retroactively before enrolling and exporting a card. Test revoked-device attempts at every endpoint, generation races/replays, account substitution, malicious-directory rollback, wrong recovery card, lost response, relay withholding, process death and removal across all device leaves. Historical message/vault backup and continuous multi-device history synchronisation remain separate designs.

## Resumable ciphertext uploads (ST-046)

This is a protocol proposal awaiting independent review; no new endpoint is enabled. Keep the existing whole-blob API for old clients. Version the staged protocol and advertise support; an unavailable staged API produces a bounded error rather than weakening capability or signature checks.

Proposed authenticated endpoints:

| Operation | Request binding | Result |
| --- | --- | --- |
| `POST /v2/blob-uploads` | uploader/device or existing capability scope; operation ID; total padded ciphertext size; ciphertext SHA-256; format version | Random upload ID, expiry, fixed chunk limit and offset 0 |
| `GET /v2/blob-uploads/{id}` | same authorisation scope | Current committed offset, expiry and completed blob ID if any |
| `PATCH /v2/blob-uploads/{id}` | ID, expected offset, chunk length and body digest; fresh signed-request nonce when applicable | New committed offset or 409 with authoritative offset |
| `POST /v2/blob-uploads/{id}/complete` | ID, original size/digest, operation ID, same scope | Existing or new immutable blob ID |
| `DELETE /v2/blob-uploads/{id}` | same scope | Idempotent abort; no published blob deletion |

Use the existing encrypted attachment **ciphertext stream** unchanged; transport chunks are not new encryption chunks. Resume only with the exact persisted ciphertext, size and digest; re-encryption requires a new operation ID. No plaintext names, MIME type or unpadded length are sent to the relay. Upload IDs are identifiers, not bearer authorisation. The unauthenticated capability lane continues to require its explicit capability and quota checks on every stage. Never convert it into a device-signed sender-identifying request just for resume.

Suggested bounds for review: 1 MiB transport chunks; current 101 MiB total ceiling; 2 live sessions per uploader/capability; 202 MiB reserved aggregate per scope; fixed 24-hour session expiry. Enforce global disk/database capacity and authenticated-session creation rate limits. Reserve the **full total** atomically before accepting bytes. Completion transfers reservation to existing blob accounting exactly once; abort/expiry frees it once. Revocation blocks further writes and completion even when an upload ID is known. Session activity does not extend expiry. Configure operator ceilings rather than hard-coding unlimited new storage in the DB.

Store chunks with `(session, offset)` uniqueness and digest. Within a transaction lock the session, validate scope/expiry, accept exactly `offset == committed_offset`, then advance by the actual accepted bytes. For a duplicate earlier offset, return its result only if bytes/length/digest match a recorded chunk; mismatches fail. Future offsets, overlaps and sparse writes fail. Body read deadlines and concurrency slots cover only the bounded chunk read; never hold a slot between chunks. A lost response is resolved by status or an exact replay using a fresh request nonce. Do not replay a signed HTTP request verbatim (request anti-replay still applies).

Completion streams the recorded ciphertext in order, validates total and full digest, publishes one blob and atomically records its blob ID. Repeated completion returns that ID; conflicting completion fails. Reuse MR-016's scope-bound deduplication without revealing another scope's blob existence. Crash recovery must resolve publish/session accounting atomically. If external object storage is introduced, use an unpublished staging namespace and a durable completion journal; it is not assumed to be transactional with PostgreSQL. TTL cleanup must be race-tested against reads and completion, and must not delete final blobs through stale staging references.

Acceptance tests required before rollout: cut every boundary and resume, lost responses, concurrent same/different chunks, short/oversized bodies, hash mismatch, cross-user/cross-capability session access, revoked/expired capability, quota race/abort/TTL, finalisation replay, restart after each DB step, old/new client compatibility, zero leaked plaintext and bounded memory under slow bodies. Add a session-parser fuzz target after wire types exist. Independent review must approve the nonce/scope/capability rules and crash accounting first.

## Operator pinning and release (ST-002, ST-014)

Do not derive a trusted pin from an unauthenticated network fetch. The operator supplies two distinct `sha256/<base64 SHA-256 of SPKI>` values through an authenticated channel: the active key and an independently held backup key. Record relay host, owner, validity window, backup-key custody, signed distribution method and rotation date. Both pins must belong to keys controlled by that operator; an unrelated key is not a backup. Existing invitation-carried onion pins have a different trust model and must not be overwritten by a universal pin set.

Rotation procedure: distribute `{current,next}` authenticated by the existing contact/operator trust anchor, wait for adoption, switch the TLS key, retain overlap for offline clients, then retire the old pin through another authenticated update. Expired or unmatched pins fail closed with a visible error; never turn off pinning on failure. Emergency rotation needs an out-of-band verified invitation, with explicit user confirmation. Test current/backup/wrong pins, hostname/TLS checks, revoked old pin, clock and offline-client cases. No operator pin set was supplied.

`scripts/reproduce-release.sh` builds unsigned APK **and AAB** twice in clean checkouts at different absolute paths, compares their bytes, emits an SBOM and records input commit/toolchain/hashes. It refuses a dirty source tree and unsets release-key variables. A passing run establishes only same-host, same-toolchain reproducibility. Keep build evidence and run the same procedure on a second trusted host before broader claims.

The release owner must retain a real offline/hardware-backed signing key, its alias, encrypted offline backup and an update-key rotation plan. A newly generated agent key is not a substitute for owner custody. Sign the verified unsigned artifact using `scripts/sign-release.sh`, verify the signer digest out of band, and preserve APK v2/v3 signatures. The current signing script handles **APK only**; a signed AAB additionally needs the owner's `jarsigner` ceremony and verification. Publish `SHA256SUMS`, `PROVENANCE.txt`, SBOM and verification instructions only after signing and gate completion. `SHA256SUMS` now contains hash lines only and can be checked with `sha256sum -c`; provenance is stored separately. No real release key or signed artifact exists from this pass.

## Campaign evidence and independent review (ST-005, ST-055, ST-060)

The fuzz workflow accepts 120–14400 seconds per target; the requested campaign is **10800 seconds on each of 14 targets with AddressSanitizer**. It restores each target's corpus and preserves corpus, crash inputs, commit, actual nightly compiler, start/end, exit status and full libFuzzer log for 30 days on every outcome. Download evidence promptly; cache/artifact retention is not permanent custody. A build failure or early crash does not satisfy three hours of fuzzing. Save and reproduce each crash with the same toolchain, reduce it with `cargo +nightly fuzz tmin TARGET INPUT`, record input hash/stack trace/reproducer/cause/fix/test and reviewer disposition, then repeat the remaining campaign. Never label a corpus input safe merely because it stopped reproducing. The nightly compiler is recorded rather than reproducible across future nightly updates.

Tor measurement: one manual `android-tor` dispatch schedules **20 indexed repetitions** on a single commit, with at most three running at once; these are consecutive indexed samples, not a claim of twenty successful runs or twenty temporally serial executions. Failures are never silently rerun or excluded. Count E2E failures, provisioning failures, cancellations and timeouts separately; report all-run non-success rate and, separately, network-attributable rate with its denominator. Correlation between samples and emulator/host Tor scope prevent a phone/Orbot reliability claim. `scripts/collect-campaign.py tor RUN_ID --download` saves job timestamps, conclusions and raw logs. A completed 20-sample collection is measurement evidence, not automatic closure of ST-060: credential transmission/rotation still needs trace evidence and causes must be inspected.

`scripts/collect-campaign.py fuzz RUN_ID --download` saves fuzz job metadata and artifacts. The script records the run attempt to avoid mixing retries with the original sample. Every failure requires actual log triage; the script intentionally does not guess a cause.

The independent review brief remains `EXTERNAL_REVIEW_SCOPE.md`. Include `CROSS_RELAY_GROUPS.md`, contact-card/capability and signed-request code, **and this proposed account/push/upload design**. Require a named independent reviewer, immutable reviewed commit, scope/exclusions, severity-ranked findings, reproducible evidence and fix/retest sign-off. No reviewer was provided or contacted; author self-review and automation cannot close ST-005.
