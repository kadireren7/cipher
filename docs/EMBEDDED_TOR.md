# Embedded Tor

Since `0.2.0` development, Cipher carries its own Tor client, so the user does not install Orbot or configure a proxy. **Cipher does not implement any anonymity protocol**: the daemon is the C Tor client, packaged for Android by the Guardian Project.

## Decision

| | `info.guardianproject:tor-android` (chosen) | Arti (Tor Project, Rust) |
| --- | --- | --- |
| What it is | The C Tor daemon as an Android library, used by Orbot and OnionShare | Tor rewritten in Rust |
| Onion-service client | Yes (it is C Tor) | Behind a non-default feature flag |
| Android SDK | A maintained AAR on Maven Central, current Tor 0.4.9.x | None; would be built and bound by hand |
| Fit with Cipher | A local SOCKS5 port: the existing fail-closed route is unchanged | Would require rewriting the Kotlin transport |

Arti remains a candidate for later; nothing here prevents it.

## How it runs

* The daemon is `CipherTorService`, a subclass of the library's `TorService`, declared with `android:process=":tor"`, `android:exported="false"` and no intent filter. It is **its own process**: the C Tor code never shares an address space with the vault, the engine or the keys. `CipherApplication` returns immediately in that process, so it never opens the vault.
* The app talks to it through **one loopback SOCKS5 port** (`127.0.0.1:19050`, `IsolateSOCKSAuth`) and a one-line progress file in the app's private `no_backup/tor/`. The percentage is read from the daemon's own control connection inside the `:tor` process; nothing else (no log lines, addresses or circuit data) leaves it.
* `torrc` (generated by `TorConfig`): `ClientOnly 1`, `SafeLogging 1`, `AvoidDiskWrites 1`, `HTTPTunnelPort 0`. No relay or exit role, no DNS port, no transparent proxy, no TCP control port. The library's defaults also open an HTTP tunnel on 8118; it is switched off explicitly (found and fixed during the first emulator run, covered by a unit test).
* **Fail closed, unchanged:** the route is still one fixed SOCKS endpoint. If the daemon is not up, the connection is refused and every request fails with `RouteUnavailable`; the encrypted message stays in the outbox. There is no direct fallback and no local DNS (`NoDns`; names are resolved by Tor). TLS pinning for onion relays is unchanged.
* **Lifecycle:** Tor starts when Cipher comes to the foreground and is stopped 5 minutes after it leaves it. No wake lock, no battery-optimisation exemption, no foreground service. In the background, messages wait on the relay as before (`NOTIFICATIONS.md`).
* **Modes:** built-in Tor is the default for a new install; an external SOCKS proxy (Orbot) can still be chosen in Settings. Choosing the external proxy stops the built-in daemon. A build never uses both.
* **Bridges:** plain bridges only (`IP:port [fingerprint]`). Pluggable transports (obfs4, snowflake, webtunnel) need a transport binary that is not shipped, so they are refused with an error rather than silently ignored. Each bridge line is validated as a whole, single-line string, so it cannot smuggle another torrc directive.

## Supply chain

* Artifact: `tor-android-0.4.9.14.aar` from Maven Central (plus `jtorctl` 0.4.5.7 and `androidx.localbroadcastmanager`). SHA-256 values are pinned in `gradle/verification-metadata.xml` (the AAR hash was computed independently and matches).
* The publisher's detached PGP signature verifies against key `A801183E69B37AA9` ("Nathan of Guardian", Guardian Project). The key is not in a web of trust, so this proves the artifact is what that key signed, not who that person is.
* The library requires `compileSdk` 37.1, so the project now compiles against 37.1 (and suppresses AGP 8.13's "max recommended 36" notice). This is compile-time only; `targetSdk` (35) and `minSdk` (30) are unchanged, so runtime behaviour does not change. Older library versions that compile against API 36 carry an older Tor and were not chosen.
* Cost: about 7.6 MB (`arm64-v8a`) and 8.4 MB (`x86_64`) of native code.

## What was verified (emulator, API 34 x86_64, Tor over the real network)

* The `:tor` process starts, reports 100 % bootstrap, and its progress file stays fresh.
* The only listener the app opens is `127.0.0.1:19050` (HTTP tunnel off).
* A fresh install registers against an **onion relay** (pinned self-signed certificate) through the built-in Tor with no host Tor and no `adb reverse`, then polls it continuously over Tor.
* The R8-minified **release** build also starts the daemon in its own process and the daemon reaches the onion relay (checked from the host through the forwarded SOCKS port). The release app itself was not onboarded: release builds refuse a software-only Keystore.
* Unit tests: torrc content, bridge validation (including injection attempts), progress parsing. Static guards: exactly one service, own process, not exported.

## Not verified / known limits

* **No physical device.** Doze, app standby, OEM process killers and real mobile networks are untested; so is Tor start-up time on a phone and battery use.
* **Other apps can use the SOCKS port.** It is loopback-only, but any app on the phone can connect to `127.0.0.1:19050` and borrow the circuit. They cannot read Cipher's traffic; Orbot behaves the same. (Tracked as ST-064.)
* **Fixed port.** If something else already uses 19050 the daemon cannot start and Cipher stays fail-closed ("Privacy route unavailable"); there is no automatic port fallback yet.
* **Tor is visible to the ISP** and bridges are limited to plain ones (ST-043).
* **Process isolation is Android's, not a sandbox:** both processes share the app's uid and data directory.
* Network-level proof of "no DNS leak / no clear-network connection" beyond the fail-closed design and static checks (a packet capture on a device) has not been produced.
